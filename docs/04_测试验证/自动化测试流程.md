# 自动化测试与节点验收流程

本文是 Medical BI Designer 的开发测试门禁。每个开发节点只有在规定的自动化检查全部通过、缺陷已分级并记录后，才允许标记为完成并进入下一节点。

## 1. 质量目标

- 功能正确：验收条件至少包含正常、边界、空值、非法输入和错误恢复。
- 兼容稳定：V1/V2/V3 读取、迁移、保存与导出不得回归。
- 数据安全：客户端不得提交 SQL、字段名或运算符；医疗数据、凭据和私有地址不得进入测试夹具与报告。
- 运行可靠：页面无未捕获异常，API 错误可定位，相同输入行为确定。
- 可追溯：需求、代码、测试用例、执行结果和遗留风险能够对应到同一节点。

## 2. 测试金字塔

| 层级 | 覆盖内容 | 执行时机 | 失败处理 |
| --- | --- | --- | --- |
| 静态检查与构建 | TypeScript、Vue 模板、生产打包 | 每个节点 | 阻断节点完成 |
| 单元测试 | 纯函数、模型、校验、状态机、缓存 | 每次行为变更及节点完成 | 阻断提交与合并 |
| 契约/集成测试 | Schema、迁移、存储、API 请求与 SQL 编译结果 | 每个节点 | 阻断节点完成 |
| 浏览器关键链路 | 设计器、参数中心、数据集、数据源、保存/刷新 | UI 节点及全量门禁 | 阻断节点完成 |
| 安全与依赖检查 | 危险输入、凭据边界、npm 高危漏洞 | 全量门禁与 CI | 高危问题阻断发布 |
| 真实库验收 | 固定只读验证库与校验 SQL 对账 | 涉及查询语义的阶段关闭 | 不通过不得阶段验收 |

## 3. 节点完成流程

1. **定义完成标准**：开发前写明验收条件、影响模块、兼容边界和风险。
2. **先补测试**：新增行为必须有对应测试；修复缺陷必须先形成可复现用例。
3. **开发中快速反馈**：执行相关测试文件，避免把问题累积到节点末尾。
4. **节点门禁**：执行 `npm run verify:node -- <节点>`。脚本会先跑节点定向测试，再跑全量单元回归和生产构建；UI 节点还会跑 Chromium 关键链路。
5. **阶段全量门禁**：执行 `npm run verify:full`，包含全量测试、构建、浏览器测试和高危依赖审计。
6. **人工验收补充**：仅对视觉一致性、真实数据库结果对账、可用性等不适合稳定自动断言的内容人工验收，并保存截图或对账记录。
7. **形成记录**：记录命令、通过数、失败数、环境、缺陷、遗留风险和结论。没有证据不得写“已完成”。

门禁执行结果同时写入 `test-results/latest-gate.json`；该目录不提交仓库，CI 失败时保留 Playwright 报告供排查。

## 4. Phase8 节点测试矩阵

| 节点 | 必备定向测试 | 重点断言 | 浏览器 |
| --- | --- | --- | --- |
| P8.0 | Phase1 与 Phase7 交付基线 | 旧计算语义与 V3 交付样例不变 | 否 |
| P8.1 | `phase8-dashboard-schema.test.ts` | 新类型、Schema、旧模型兼容、错误路径 | 否 |
| P8.2 | `phase8-parameter-runtime.test.ts` | 初始化、批量提交、清空、来源、事务去重、必填校验 | 否 |
| P8.3 | `phase8-parameter-binding.test.ts` | 精确匹配、别名、人工映射、重复和类型冲突 | 否 |
| P8.4 | `phase8-query-parameters.test.ts` | 占位符、空值、多选、日期范围、未知参数、注入输入 | 否 |
| P8.5 | `phase8-controls-refresh.test.ts` | 控件提交、依赖图、定向刷新、相同值不刷新 | 是 |
| P8.6 | `phase8-query-cache.test.ts` | 查询键、并发合并、TTL、失败不缓存、强制刷新 | 否 |
| P8.7 | 上述全部 | 保存、刷新、重新导入、旧版本回归、完整交付 | 是 |

规定的节点测试文件不存在时，门禁直接失败，防止“代码完成但测试后补”。

## 5. 用例设计标准

每项业务规则至少考虑以下等价类：

- 正常值与最小可用值；
- `undefined`、`null`、空字符串、空数组；
- 类型错误、越界、重复、倒序范围；
- 中文、特殊字符和注入式字符串；
- 旧版本数据、未知扩展字段、损坏数据；
- 重复执行、并发执行、刷新/重载后的幂等性；
- 服务不可用、超时和失败后的状态恢复。

测试名称使用可读的业务结果描述；测试数据全部为合成数据。禁止在快照、日志、截图和 fixture 中写入真实患者数据、密码、内网地址或内部 SQL。

## 6. 缺陷与放行标准

| 级别 | 示例 | 节点/发布规则 |
| --- | --- | --- |
| S0 致命 | 数据泄露、数据破坏、任意 SQL、系统不可用 | 立即停止，必须修复 |
| S1 严重 | 主链路失败、迁移丢失、错误结果无提示 | 必须修复 |
| S2 一般 | 次要功能错误、有明确绕行方案 | 原则上修复；延期需记录责任人与计划 |
| S3 轻微 | 文案、低影响视觉偏差 | 可记录后放行 |

自动化测试、构建、S0/S1 缺陷任一未清零，节点不得标记完成。测试若因环境原因跳过，必须说明原因、替代证据和补测时间，不能按“通过”统计。

## 7. 常用命令

```powershell
# 当前节点完成门禁
npm run verify:node -- P8.2

# 阶段、PR 或发布前全量门禁
npm run verify:full

# 单独执行
npm test
npm run build
npm run test:e2e
```

首次在新机器执行浏览器测试前安装 Chromium：

```powershell
npx playwright install chromium
```
